# S4: Procrastinate periodic/stalled/schema/lock and the AsyncPostgresSaver lock

Date: 2026-11-05. Brief: `docs/tasks/S4-procrastinate-checkpointer.md`.

Versions (from `run.sh`): Python 3.14.8, procrastinate 3.10.0, croniter 6.2.4, langgraph 1.2.19, langgraph-checkpoint 4.3.1, langgraph-checkpoint-postgres 3.2.0, psycopg 3.3.8, psycopg-pool 3.3.3, PostgreSQL 18.6 (compose). The schema check also installs procrastinate 3.0.0 in an isolated `uv run --no-project` env.

## Question

1. Can one periodic task per manifest cron be registered from data at runtime, with kwargs? Cron format, timezone, what the task receives.
2. Stalled jobs: exact API, heartbeat settings and defaults; is a killed worker's job requeued?
3. Schema: how to apply it, and a scripted upgrade path between versions.
4. `lock=<thread_id>`: same lock sequential, different locks parallel; what happens when the first job fails and retries.
5. `AsyncPostgresSaver`: per-instance write serialization, measured (one instance vs two vs the platform's `PooledPostgresSaver`); checkpointer pool sizing.

## Results

### Check 1: periodic tasks from data: PASS

Working snippet (from `periodic_check.py`):

```python
@app.task(name="fire_cron")
async def fire_cron(timestamp: int, periodic_id: str, flow: str, input: dict) -> None: ...

for i, cron in enumerate(CRONS):  # data from the manifest
    periodic_id = f"{cron['flow']}:{i}"
    kwargs = {"periodic_id": periodic_id, "flow": cron["flow"], "input": cron["input"]}
    app.periodic(cron=cron["schedule"], periodic_id=periodic_id, task_kwargs=kwargs)(fire_cron)
```

Output (trimmed):

```

duplicate (periodic_id, timestamp) jobs in DB: []
fired report:2 ts=1793847600 (2026-11-05T03:00:00+00:00) input={} lag=117.01s

```

- **Registration**: `app.periodic(cron=, periodic_id=, **configure_kwargs)` wraps an existing `Task`; call it in a loop before the worker starts. One task can carry many schedules: the registry key is `(task.name, periodic_id)` and a duplicate raises `TaskAlreadyRegistered` (`periodic.py:83-89`). `periodic_id` and `task_name` are `varchar(128)` (`schema.sql:83,86`).
- **What the task gets**: `task_kwargs` plus `timestamp` (int, epoch seconds of the scheduled firing, not of the run). Procrastinate writes `timestamp` into the registered `task_kwargs` dict in place (`periodic.py:209-213`): build a fresh dict per registration.
- **Cron format**: 5 fields, or 6 with seconds as the LAST column (`blueprints.py:370`, croniter). The first run of this check used `*/2 * * * * *` and fired every second of even minutes, because croniter reads the first field as minutes.
- **UTC**: the deferrer evaluates croniter on `time.time()` floats (`periodic.py:141-187`), so schedules are UTC whatever the `TZ`: `0 3 * * *` fired at 03:00:00Z while local time was 00:00 -03.
- **One firing cluster-wide, for the latest timestamp only**: every worker runs a deferrer (`worker.py:126,610`); `procrastinate_defer_periodic_job_v2` inserts into `procrastinate_periodic_defers` with `UNIQUE (task_name, periodic_id, defer_timestamp)` and `ON CONFLICT DO NOTHING` (`schema.sql:87,162-170`). Two workers in step: zero duplicate jobs. But the same function then deletes every row of that periodic task with an older timestamp (`schema.sql:193-204`), and each deferrer walks forward from its own in-memory last firing (`periodic.py:119,161-164,171-177`). A deferrer that lags more than one period (event loop stall, suspended host) re-inserts an older timestamp whose row is gone, so that firing runs twice (`sweep_check.py`):

  ```
  periodic defers ['B:T60', 'B:T120', 'A (lagging):T60'] -> job ids [1, 2, 3]
  fire_cron jobs by timestamp: [60, 120, 60]
  runs inserted per job (uuid5 key + ON CONFLICT DO NOTHING): [1, 1, 0]
  ```

  Cron tasks must therefore be idempotent per `(periodic_id, timestamp)`; the last line shows the guard recommended for T25.
- **Startup catch-up**: a deferrer with no memory of a task (worker start) defers only the LAST past firing (`get_prev`, `periodic.py:178-198`), and only if it is at most `max_delay` old; earlier missed firings are dropped (`report:2` and `report:3` above, lags of 117 s and 57 s). `max_delay` defaults to `MAX_DELAY` = 600 s (`periodic.py:22`) and is set with `App(periodic_defaults={"max_delay": ...})` (`app.py:83,106`; passed to the deferrer at `worker.py:126-130`). A worker restart does not re-fire, because the defers row already exists, as long as `periodic_id` stays the same.

### Check 2: stalled jobs: PASS

API (`manager.py:223-271,512-547`; `worker.py:48-49`):
- `await app.job_manager.get_stalled_jobs(queue=None, task_name=None, seconds_since_heartbeat=30)` returns `doing` jobs whose worker has a heartbeat older than the threshold, or whose `worker_id` is NULL (`queries.sql:39-53`). `nb_seconds=` is the deprecated pre-heartbeat mode.
- `await app.job_manager.retry_job(job, retry_at=None, priority=None, queue=None, lock=None)` moves `doing`/`failed` back to `todo`, `attempts + 1`, `scheduled_at = retry_at or now` (`schema.sql:364-402`).
- Worker defaults: `update_heartbeat_interval=10.0`, `stalled_worker_timeout=30.0`. A worker deletes dead worker rows (`prune_stalled_workers`) only when it starts (`worker.py:445-449`).

Output:

```
worker 1 SIGKILLed while J1 runs
[after kill] jobs=[(1, 'J1', 'doing', 't1', 0, 1), (2, 'J2', 'todo', 't1', 0, None)] workers=[1]
get_stalled_jobs right after kill: []
[w2 running, 5s later] jobs=[(1, 'J1', 'doing', 't1', 0, 1), (2, 'J2', 'todo', 't1', 0, None)] workers=[1, 2]
get_stalled_jobs: [(1, 'J1', 0)]
[after retry_job] jobs=[(1, 'J1', 'todo', 't1', 1, 1), (2, 'J2', 'todo', 't1', 0, None)] workers=[1, 2]
[done] jobs=[(1, 'J1', 'succeeded', 't1', 2, 2), (2, 'J2', 'succeeded', 't1', 1, 2)] workers=[1, 2]
log: [('J1', 'start'), ('J1', 'start'), ('J1', 'end'), ('J2', 'start'), ('J2', 'end')]
```

- **No self-healing.** A new worker does not requeue the dead worker's job (still `doing` 5 s later). Only `get_stalled_jobs` + `retry_job` do.
- **The stalled job blocks its whole lock.** J2 (same `lock=t1`) stays `todo` until J1 is retried and finishes. Worst-case thread latency after a crash: `seconds_since_heartbeat` (30) + sweep period (60 s).
- **The job re-runs from the start** (J1 `start` twice). For `execute_run` this is the claim's job: the re-run either wins the claim or exits.
- **`retry_job` counts as an attempt**: J1 ended with `attempts=2`. Stalled requeues and the task's own `RetryStrategy` share that counter.
- **A live worker (W1) whose event loop stalls longer than `seconds_since_heartbeat` looks dead too**: the sweep retries or closes its job while W1 still runs it. Not tested here; read from the code.
  - The run is covered by the lease claim + fence + partial unique index: the re-run exits at the claim while W1's lease is live. If the stall also outlasts the lease, the new claim wins and the fence rejects W1's heartbeat and finish, so a node can run twice for at most `runs.heartbeat_s` after W1 wakes (the design's existing open check on lease expiry).
  - Procrastinate's side does not converge: if the sweep closed the job `failed` (step 2 below), W1's own `finish_job` (`worker.py:187`) raises "not in doing or todo status" (`schema.sql:288-290`). The exception is unhandled in the job task and the worker continues (the done-callback only frees the slot, `worker.py:423-433`). The job then reads `failed` while the run is `success`: **T24 must never read the Procrastinate job status as run status**.
  - A plain `retry_job` gives the analogous case: `finish_job` accepts `todo` or `doing` (`schema.sql:282-290`), so W1 can finish the requeued job, and whichever of W1 and the re-run finishes second raises the same error.

**`retry_job` fails when the run was re-deferred (`sweep_check.py`).** `retry_job` sets the job to `todo` (`schema.sql:364-402`), so it hits `procrastinate_jobs_queueing_lock_idx_v1` (unique `queueing_lock` among `todo` jobs, `schema.sql:100`) when another `todo` job of the same run exists, e.g. the orphan sweep or the API re-deferred `execute_run(run_id)` while the dead job was still `doing` (accepted, check 4). The stalled job then stays `doing` forever, holding `lock=thread_id`, and the thread is wedged: the `todo` job is never fetched while a same-lock job is `doing` (`schema.sql:232-236`).

```
A requeue_stalled: [('R1', 'retried')]
A orphan re-defer after it: AlreadyEnqueued
A jobs: [(4, 'todo')]
B orphan re-defer while doing: deferred
B plain retry_job -> UniqueViolation procrastinate_jobs_queueing_lock_idx_v1
B jobs after plain retry: [(6, 'doing'), (7, 'todo')]
B requeue_stalled: [('R2', 'finished FAILED (a todo job with its queueing_lock exists)')]
B jobs: [(6, 'failed'), (7, 'todo')]
C requeue_stalled: [('R3', 'skipped: Job was not found or has an invalid status to retry (job id: 8)')]
worker ran: ['R1', 'R2']
B jobs after worker: [(6, 'failed'), (7, 'succeeded')]
```

Recommended sweep (the `requeue`/`requeue_stalled` functions in `sweep_check.py`):
1. Stalled jobs FIRST, orphan re-defer after: a requeued job is `todo` and holds the queueing lock, so the re-defer gets `AlreadyEnqueued` (A).
2. Per stalled job: `retry_job(job)`; on `procrastinate.exceptions.UniqueViolation` with `constraint_name == procrastinate.manager.QUEUEING_LOCK_CONSTRAINT` (`manager.py:15`, raised by `sync_psycopg_connector.py:30-42`), close it with `await app.job_manager.finish_job(job, status=Status.FAILED, delete_job=False)` (`manager.py:317-335`, `from procrastinate.jobs import Status`): the lock frees and the `todo` job runs (B). Ordering alone is not enough: the conflicting job can come from an earlier sweep or from the API.
3. Catch `procrastinate.exceptions.ConnectorException` per job (its `__cause__` is the psycopg error) and continue: a job that left `doing` between `get_stalled_jobs` and `retry_job` raises "invalid status to retry" (C), and `finish_job` raises "not in doing or todo status" on the same race (`schema.sql:288-290`).

**The sweep itself must not take `lock=` (`sweep_check.py`, 2c).** The sweep job can stall too: with `lock="sweep"`, a sweep left `doing` by a dead worker makes fetch skip every later sweep (`schema.sql:232-236`, same mechanism as J2 above), so stalled and orphan recovery stops cluster-wide, silently, until someone fixes the job by hand. Dropping `lock=` alone lets two sweeps overlap and both retry or close the same job, which one of them may already have handed to a live worker. The sweep therefore keeps `queueing_lock="sweep"` (dedupes firings while `todo`) and excludes concurrent runs with `pg_try_advisory_xact_lock(<named constant>)`, taken inside a transaction on a dedicated connection held for the whole sweep; not acquired means return. A transaction-scoped lock leaves no session state (rule 1d), and Postgres releases it when the worker's connection dies:

```
a sweep 1 (worker subprocess) holds the advisory lock: True
a after SIGKILL: lock held = False
a sweep jobs after kill: [(9, 'doing')]
a next firing (queueing_lock only dedupes todo): deferred
a sweeps run by the next worker: ["ran, requeue_stalled=[('sweep', 'retried')]", 'ran, requeue_stalled=[]']
a sweep jobs: [(9, 'succeeded'), (10, 'succeeded')]
b two concurrent sweeps: ['ran, requeue_stalled=[]', 'skipped']
```

The next sweep also requeues the dead sweep job (it is a stalled job like any other); its re-run takes the lock and finds nothing to do. The lock connection sits `idle in transaction` while the sweep works on Procrastinate's pool: `idle_in_transaction_session_timeout` (off by default) must stay above the sweep's duration.

### Check 3: schema install and upgrade path: PASS

- **Fresh install**: `await app.schema_manager.apply_schema_async()` (or `SchemaManager.get_schema()` run as one script). It is **not idempotent**: `reapply s4_fresh: ... DuplicateObject: type "procrastinate_job_status" already exists`.
- **Upgrade**: Procrastinate has no applied-migrations table (it dropped its version table in 0.5, `migrations/00.05.00_03_drop_procrastinate_version_table.sql`); docs: "It's your responsibility to keep track of which migrations have been applied". Files ship in `SchemaManager.get_migrations_path()` (`procrastinate/sql/migrations/`), named `xx.yy.zz_ab_{pre|post}_*.sql`. None contains `CONCURRENTLY` or `BEGIN/COMMIT`, so each can run in one transaction.
- **Scripted path, proven 3.0.0 -> 3.10.0**:
  1. Fresh install: apply `schema.sql` and, in the same transaction, record EVERY shipped migration file name as applied (the baseline).
  2. Upgrade: apply, in file-name order, every shipped file not yet recorded, one transaction per file plus its record row.
  3. Run it under the existing migrations advisory lock.

```
install s4_upgrade: procrastinate 3.0.0, baseline=31 files, last=03.00.00_50_post_cancel_notification.sql
upgrade s4_upgrade: procrastinate 3.10.0, applied=['03.01.00_01_pre_add_heartbeat.sql', '03.01.00_50_post_add_heartbeat.sql', '03.02.00_01_pre_batch_defer_jobs.sql', '03.02.00_50_post_batch_defer_jobs.sql', '03.03.00_01_pre_priority_lock_fetch_job.sql', '03.04.00_01_pre_add_retry_failed_job_procedure.sql', '03.04.00_50_post_add_retry_failed_job_procedure.sql']
upgrade s4_upgrade: procrastinate 3.10.0, applied=[]
install s4_fresh: procrastinate 3.10.0, baseline=38 files, last=03.04.00_50_post_add_retry_failed_job_procedure.sql
compare s4_fresh vs s4_upgrade: 520 lines, diff lines=0
```

- **Why the baseline uses file names, not versions**: 3.0.0 already ships its own `03.00.00_*` files inside its `schema.sql`, so the `xx.yy.zz` prefix cannot be read as "apply before upgrading to xx.yy.zz". Tracking file names needs no version arithmetic.
- **One known drift, normalized in the diff**: 3.0.0 used `json_object('type': ..., 'job_id': NEW.id)` (PG16+ syntax) in two notify trigger functions. Upstream later rewrote `schema.sql` and `03.00.00_01_pre_cancel_notification.sql` in place to `json_build_object(...)`, with no new migration. Both are equivalent on PG 18; without the normalization the raw diff is exactly those 2 lines. Consequence: upstream can edit shipped files in place, and a name-based tracker will not re-apply them (acceptable here).
- **Pre/post**: `pre` before the new code, `post` after it. Zero-downtime upgrades need one deploy per migrating version. The simple path, applying all pending files with every Procrastinate user stopped (API defers too), is the one the docs call "with service interruption".

### Check 4: `lock=` semantics: PASS

```
queueing_lock while todo: second defer -> AlreadyEnqueued
queueing_lock while doing: second defer ACCEPTED (waits on lock q)
final jobs: [... ('C1', 'succeeded', 2), ('C2', 'succeeded', 1), ('E1', 'failed', 3), ('E2', 'succeeded', 1), ...]
(0.13, 'A1', 'start') (0.13, 'B1', 'start') (1.13, 'A1', 'end') (1.28, 'A2', 'start')
(0.33, 'C1', 'fail attempt 1') (2.5, 'C1', 'start attempt 2') (2.7, 'C1', 'end') (2.71, 'C2', 'start')
(0.34, 'E1', 'fail attempt 1') (2.71, 'E1', 'fail attempt 2') (4.73, 'E1', 'fail attempt 3') (4.94, 'E2', 'start')
```

- **Same lock runs sequentially** (A2 starts after A1 ends); **different locks run in parallel** (B1 overlaps A1).
- **A failing job keeps the lock through its retry wait.** C2 did not run in the 2 s between C1's failure and its retry; it ran only after C1 succeeded. The reason is in `procrastinate_fetch_job_v2` (`schema.sql:220-252`): a job is skipped while any job with the same lock is `doing`, or is `todo` with a higher priority or the same priority and a lower id, even if that job's `scheduled_at` is in the future. The fetch orders by `priority DESC, id ASC` (`schema.sql:236-251`), so order per lock is strict FIFO only while every job of the lock has the same priority, and a retry backoff delays every later job on that thread.
- **Exhausted job**: E1 ends `failed` and releases the lock, so E2 runs.
- **`RetryStrategy(max_attempts=N)` means N retries, so N+1 executions**: E1 ran 3 times with `max_attempts=2`. The decision reads `job.attempts` before the increment (`retry.py:197`); `finish_job`/`retry_job` increment it (`schema.sql:282-283,388`).
- **`queueing_lock` dedupes only `todo` jobs** (unique index `WHERE status = 'todo'`, `schema.sql:100`). A second `execute_run(run_id)` deferred while the first is `doing` is accepted, then waits on the thread lock. The claim makes that second job exit, but it also makes a later `retry_job` of the first job fail if that one is stalled (check 2, `sweep_check.py`).
- Defer by name works without importing the task: `app.configure_task(name=..., allow_unknown=True default)` (`app.py:213-242`).

### Check 5: `AsyncPostgresSaver` lock: PASS (claim confirmed and measured)

Source (`langgraph/checkpoint/postgres/aio.py`, 3.2.0):
- `__init__` creates `self.lock = asyncio.Lock()` per instance (line 64).
- `_cursor` does `async with self.lock, _ainternal.get_connection(self.conn) as conn` (line 428) for every call: `aput`, `aput_writes`, `aget_tuple`, `alist`, `adelete_thread`, `aprune`. With a pool, `get_connection` takes a fresh pooled connection per call (`_ainternal.py`), so the lock only serializes. Its own comments justify it for a single connection or a pipeline (lines 430-441).
- `alist` yields its tuples inside `async with self._cursor()` (lines 153-183), so it holds the lock (and a connection) for the whole iteration.

Platform code under test: `packages/core/src/ranvier/_internal/runtime/checkpointer.py` (`PooledPostgresSaver` swaps the lock for `asyncio.Semaphore(pool.max_size)` when `conn` is a pool and `pipe is None`).

- **Upstream: one instance means one DB call at a time** (`inflight=1` at every pool size). Throughput stays flat at about 130-160 calls/s at 2 ms RTT, so a bigger pool does not help.
- **The lock is per instance**: two instances give `inflight=2` and about 2x throughput.
- **`PooledPostgresSaver` uses the whole pool** (`inflight` = pool size): at 2 ms RTT 576 calls/s with pool 5 (3.6x upstream x1 at the same pool size) and 814 with pool 10 (5.2x). The fix-pass re-run gave 612 (4.8x) and 833 (4.8x): about 3.5-5x at pool 5 and about 5x at pool 10.
- **Noise**: the direct rows are noisy, because other agents' integration tests share this Postgres and WSL adds jitter (pool=2 rows omitted here, see the full output). The RTT rows are the stable signal.
- **Nesting**: a nested call inside `alist` deadlocks upstream. It works with the semaphore, but costs a second connection, and deadlocks again if every permit is held by an `alist`. Keep rule 1i (never nest).

**Pool sizing recommendation**: keep `database.checkpointer_pool_max` = 10 and one `PooledPostgresSaver` per process.
- Demand: `max_active_runs` = 32 LLM-paced runs need about 2-3 checkpoint calls per superstep, with supersteps lasting seconds: roughly 100 calls/s at peak. Pool 5 already gives 576-612 calls/s (about 6x that demand) at 2 ms RTT; 10 covers fan-out bursts (parallel branches each call `aput_writes` when they finish) and a long `aprune`/`adelete_thread`, which holds one connection.
- Per-process budget: app 5 + checkpointer 10 + Procrastinate 5, plus 1 standalone LISTEN connection in worker processes. Procrastinate's `listen_notify` opens a connection outside its pool (`psycopg_connector.py:289-328`), so `log_connection_budget` undercounts worker processes by 1.

## Impact on design

Proposed `docs/design.md` edits. The orchestrator applies them.

1. §5 "Serialization, recovery and housekeeping", row "Per-thread order (queued runs)" (line 270).
   - Before: ``| Per-thread order (queued runs) | Procrastinate job `execute_run` deferred with `lock=thread_id` and `queueing_lock=run_id` (at most one queued job per run; `AlreadyEnqueued` is ignored) |``

## Impact on dependent tasks

T24 (queue + `execute_run` job):
- Defer by name: `app.configure_task(name=EXECUTE_RUN, lock=thread_id, queueing_lock=run_id).defer_async(run_id=...)`; catch `procrastinate.exceptions.AlreadyEnqueued`.
- `thread_busy` retry: `RetryStrategy(max_attempts=N, ..., retry_exceptions={ThreadBusy})` means N+1 executions. Stalled requeues consume the same `attempts`, so give it headroom (the platform's `runs.max_attempts` governs orphans, not Procrastinate's). The backoff blocks later jobs of that thread (FIFO per lock): keep it short (seconds).
- Worker: `concurrency=limits.max_active_runs`; leave heartbeat defaults (10 / 30) and name them as constants if passed explicitly.
- Integration test hints proven here: same lock sequential / different lock parallel via event timestamps; `queueing_lock` dedupe while `todo`.
- Do not pass `priority=` to `execute_run` (per-lock FIFO depends on uniform priority).

T25 (sweep, prune, crons, migrate):
- Sweep: stalled jobs first, orphan re-defer second. Per stalled job: `retry_job(job)`; on `UniqueViolation` with `constraint_name == manager.QUEUEING_LOCK_CONSTRAINT`, `finish_job(job, status=Status.FAILED, delete_job=False)`; catch `ConnectorException` per job and continue (`requeue_stalled` in `sweep_check.py` is the reference). Register it with `app.periodic(cron="* * * * *", periodic_id="sweep", queueing_lock="sweep")` and NO `lock=`: a duplicate firing while one is `todo` gets `AlreadyEnqueued`, which the deferrer logs and skips (`periodic.py:229-240`); a `lock=` would let one dead sweep block every later sweep. Exclude overlapping sweeps (a firing deferred while one is `doing`, a stalled-but-alive sweep requeued) with `pg_try_advisory_xact_lock(SWEEP_LOCK_KEY)` (named constant) inside a transaction on a dedicated connection held for the whole sweep; return if not acquired (the `sweep` task in `sweep_check.py` is the reference). Never a session advisory lock on a pooled connection (rule 1d). Requeue every stalled job, the sweep's own dead jobs included, so the generic `requeue_stalled` path closes them.
- Integration test hint (sweep): defer `execute_run(R)`, set its job `doing` with `worker_id` NULL, defer `execute_run(R)` again (accepted), run the sweep, assert the jobs end `[failed, succeeded]` and the run executed once (scenario B of `sweep_check.py`).
- Integration test hint (kill mid-sweep): run the sweep in a worker subprocess with a test hook that holds it after the advisory lock is taken, wait for the lock in `pg_locks` (`locktype = 'advisory'`, `objid = SWEEP_LOCK_KEY`), SIGKILL the worker, defer the next firing (accepted), start a worker with a small `update_heartbeat_interval`, and assert a sweep runs and both sweep jobs end `succeeded` (scenario 2c-a of `sweep_check.py`). Plus two concurrent sweep calls: exactly one skips (2c-b).

ON CONFLICT DO NOTHING`; on conflict, skip the defer (a lagging deferrer re-defers an old firing, check 1).
