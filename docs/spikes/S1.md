# S1: LangGraph runtime checks (RunControl, context, checkpoint metadata)

Versions (from `uv.lock`, printed by the script): Python 3.14.8, langgraph 1.2.19, langgraph-checkpoint 4.3.1, langgraph-checkpoint-postgres 3.2.0, langchain-core 1.7.6, langchain 1.4.9.

Run all checks (exit 0 and `ALL CHECKS PASSED` on success; every check asserts its result):

```
uv run python bench/spikes/S1/checks.py
```

Source paths below are relative to `.venv/lib/python3.14/site-packages/`. Postgres was not available (no docker in this environment); Postgres claims are from source only and marked as such.

## Question

1. How is `RunControl` imported, built and passed to `astream`, and what does `request_drain()` do (checkpoint timing, exception, thread state, resume)?
2. Does `astream(..., context=RunContext(...))` reach `runtime.context` in nodes with and without `context_schema`?
3. Does `config["metadata"]["run_id"]` land in `checkpoint.metadata` of the latest checkpoint, and how is it read back?
4. Bonus: exact shape of `version="v2"` stream parts (updates, values, messages, custom, interrupts).

## Method

One asyncio script, `bench/spikes/S1/checks.py`, with `InMemorySaver` and plain `StateGraph`s:

- Drain: graph `a -> b -> c`; a side task waits until `b` is running, calls `control.request_drain("sigterm")`, then lets `b` finish. Repeated for `durability` `sync`, `async`, `exit`; then reuse of the drained control; then resume with `None` and a fresh `RunControl`. Variants: drain inside a subgraph (`subgraphs=True`), drain during the last node.
- Context: same node reading `runtime.context`, compiled with `context_schema=RunContext` and without; instance vs dict; nested subgraph.
- Metadata: interrupting graph, run A then `Command(resume=...)` as run B; read `saver.aget_tuple(...)` and `graph.aget_state(...)`.
- Recovery input: cancel the `ainvoke` task while node `b` hangs (orphaned run), then re-invoke with the same and with a different `metadata.run_id`; same for a run whose input was `Command(resume=...)`.
- v2 parts: parent graph with a subgraph node calling `GenericFakeChatModel` and `get_stream_writer()`, then an `interrupt()` node, `stream_mode=["updates","values","messages","custom"]`, `subgraphs=True`.

## Results

### 1. RunControl: PASS

- Import: `from langgraph.runtime import RunControl` (`langgraph/runtime.py:19` `__all__`, class at `:79-104`). No other public re-export (only internal imports in `pregel/main.py:175`, `pregel/_loop.py:135`).
- Constructor: `RunControl()` with no arguments. API: `request_drain(reason: str = "shutdown")`, properties `drain_requested: bool`, `drain_reason: str | None`. A single attribute write, documented as safe from any thread (`runtime.py:85-88`), so a signal handler or another task may call it.
- Parameter: keyword `control: RunControl | None = None` on `astream` (`pregel/main.py:3168`), and on `stream`, `invoke`, `ainvoke` and the other entry points (`main.py:2717-4112`). Without it, LangGraph builds a private one (`main.py:3406`: `control or parent_runtime.control or RunControl()`), so the caller must pass its own to be able to drain. Subgraphs inherit the parent's control through the runtime merge.
- Where it acts: `pregel/_loop.py:683-688`, in `tick()`, before scheduling the next superstep and after the `interrupt_before` check. The running superstep is not cancelled: nodes already running finish and their checkpoint is written as usual; then the loop sets status `draining` and `astream` raises `langgraph.errors.GraphDrained(reason)` (`pregel/main.py:3581-3584`; class at `errors.py:55-65`, subclass of `GraphBubbleUp`, attribute `reason`, message `"Graph drained: <reason>"`).
- Output (identical for `sync`, `async`, `exit`):

```
raised langgraph.errors.GraphDrained: reason='sigterm' msg=Graph drained: sigterm GraphBubbleUp=True
updates streamed before drain: [{'a': {'log': ['a']}}, {'b': {'log': ['b']}}]
state after drain: {'log': ['a', 'b']} next: ('c',) metadata: {'source': 'loop', 'step': 2, 'run_id': 'run-1'}
reused drained RunControl -> GraphDrained again; calls: ['a', 'b']
resume(None) output: {'log': ['a', 'b', 'c']} calls: ['a', 'b', 'c']
```

- Thread state after drain: the latest checkpoint holds the drained superstep (`b` included), `next == ('c',)`, `metadata.run_id` is the drained run. Resume with `None` input and a fresh `RunControl` runs only `c`; no node runs twice.
- A drained `RunControl` stays drained: reusing it raises `GraphDrained` again before any node runs (`runtime.py:82-83` says to create one per run).
- Drain during the last superstep: no exception, the run completes normally (`no GraphDrained; output: {'log': ['only']} next: ()`). The runner must treat "drain requested but run finished" as a normal success.
- Drain inside a subgraph: `GraphDrained` propagates to the caller; parent `next == ('inner',)`, subgraph `next == ('c',)`; resume with `None` continues inside the subgraph without re-running `a`/`b` (calls `['pre', 'a', 'b', 'c', 'post']`). The duplicated `'pre'` in the output is the shared-key reducer, identical in the no-drain baseline.
- Postgres: not run. The drain path is in the loop, not the saver, so no saver-specific behavior is expected (inference, not measured).

### 2. Runtime context without `context_schema`: PASS

`pregel/main.py:3398-3399` builds `Runtime(context=_coerce_context(self.context_schema, context))`; `_coerce_context` (`main.py:4530-4557`) returns the value unchanged when the schema is `None`, and only coerces a `dict` into a dataclass/pydantic schema.

```
with: RunContext RunContext(run_id='r1', ...)
without: RunContext RunContext(run_id='r1', ...)
without_dict: dict {'run_id': 'r1'}
with_dict: RunContext RunContext(run_id='r1', thread_id='t4', ...)
none_passed: NoneType None
with schema + incomplete dict -> TypeError RunContext.__init__() missing 5 required positional arguments: ...
subgraph (no schema anywhere): RunContext(run_id='r1', ...)
```

- Passing a `RunContext` instance reaches `runtime.context` as the same object with or without `context_schema`, and in subgraphs.
- There is no failure mode for the instance case. `context_schema` only matters for typing/schema export and for dict coercion; an incomplete dict with a dataclass schema raises `TypeError` at run start.

### 3. `metadata.run_id` in checkpoint metadata: PASS (InMemorySaver), PARTIAL (Postgres, source only)

`checkpoint/base/__init__.py:786-804` (`get_checkpoint_metadata`) copies every key of `config["metadata"]` and `config["configurable"]` into the checkpoint metadata unless the key is already set by the loop, is in `EXCLUDED_METADATA_KEYS` (`:826-836`), or starts with `__`; only `str`/`int`/`bool`/`float` values are copied. `InMemorySaver.put` uses it (`checkpoint/memory/__init__.py:463`); `AsyncPostgresSaver.aput` uses `get_serializable_checkpoint_metadata`, which wraps it (`checkpoint/postgres/aio.py:307`).

```
after run-A (interrupted): latest metadata = {'source': 'loop', 'step': 0, 'parents': {}, 'run_id': 'run-A'}
run_id per checkpoint (newest first): [('loop', 'run-A'), ('input', 'run-A')]
after run-B (resume): aget_tuple().metadata['run_id'] = run-B | aget_state().metadata['run_id'] = run-B
run_id per checkpoint (newest first): [('loop', 'run-B'), ('loop', 'run-B'), ('loop', 'run-A'), ('input', 'run-A')]
dict value dropped, int kept: {'run_id': 'r', 'obj': None, 'n': 3}
top-level config['run_id'] only -> metadata: {'source': 'loop', 'step': 0, 'parents': {}}
```

- Every checkpoint written by a run carries that run's `metadata.run_id`, including the first (`source='input'`) one.
- Read back: `(await checkpointer.aget_tuple({"configurable": {"thread_id": tid}})).metadata.get("run_id")`, or `(await graph.aget_state(config)).metadata["run_id"]`. Use `.get`: threads written without it have no key.
- `run_id` must be a `str` (UUIDs as `str(uuid)`); other types are dropped silently. LangChain's top-level `config["run_id"]` is not copied.
- LangGraph itself uses this key: `pregel/_loop.py:931-951` treats the input as a re-entry ("resume") when `config["metadata"]["run_id"]` equals the latest checkpoint's `metadata["run_id"]`, ignoring the input:

```
after cancel: values {'log': ['input', 'a']} next ('b',) run_id run-1
same run_id + original input -> {'log': ['input', 'a', 'b']} calls: ['a', 'b', 'b']
new run_id + original input  -> {'log': ['input', 'a', 'b', 'input', 'a', 'b']}
interrupted + same run_id + original input -> {'log': [], '__interrupt__': [...]} next ('ask',)
```

  So for the design's recovery rule, `None` and "original input with the same `metadata.run_id`" behave the same once a checkpoint carries the run id; the node that was running when the process died (`b`) runs again, as expected.
- Recovery of a run whose input was `Command(resume="yes")`, crashed after the resumed node checkpointed: both `None` and the same `Command` again continue from `slow`, and the replayed resume value does not answer a later `interrupt()` (`next == ('ask2',)` in both).
- Postgres: not executed here. Same metadata function as in-memory per source; the metadata column is JSONB (`aio.py:307`). Verify in T11 against the compose Postgres.

### 4. v2 stream parts (bonus): PASS

Each part is a plain `dict` (TypedDicts in `langgraph/types.py:273-362`). `ns` is `()` at the root and `("<node>:<task_id>", ...)` inside subgraphs.

| type | keys | `data` |
|------|------|--------|
| `updates` | `type, ns, data` | `{node_name: node_output}`; interrupt: `{"__interrupt__": (Interrupt(value=..., id=..., response_schema=None),)}` |
| `values` | `type, ns, data, interrupts` | full state; `interrupts` is `()` or the tuple of pending `Interrupt`s |
| `messages` | `type, ns, data` | `(AIMessageChunk, metadata)`; metadata includes `langgraph_node`, `langgraph_step`, `langgraph_path`, `langgraph_triggers`, `langgraph_checkpoint_ns`, `checkpoint_ns`, `ls_provider`, `ls_model_type`, plus `config["metadata"]` (`run_id`, `thread_id`) |
| `custom` | `type, ns, data` | the object passed to `get_stream_writer()(...)` |

- An interrupt appears twice when both modes are requested: as `updates` with `__interrupt__` and as the final `values` part with non-empty `interrupts`. Then the stream ends normally (no exception).
- A resume stream starts with a `values` part of the current state (`interrupts=()`).
- Message chunk ids look like `lc_run--<uuid>` and match the final `AIMessage.id` in `updates`.

## Impact on design

Proposed edits to `docs/design.md` (the orchestrator applies them):

1. §4, end of "What `target` may resolve to":
   - Before: `Flows declare \`context_schema=RunContext\` to get a typed \`runtime.context\`.`
   - After: `The runner always passes a \`RunContext\` instance, so \`runtime.context\` is that object whether or not the flow declares \`context_schema\`; declaring \`context_schema=RunContext\` is optional and only adds typing (S1).`
2. §5 "Single runner" step 3:
   - Before: `graph.astream(input, config, context=RunContext(...), stream_mode=[...], subgraphs=True, version="v2", durability=flow.durability)`
   - After: `graph.astream(input, config, context=RunContext(...), control=RunControl(), stream_mode=[...], subgraphs=True, version="v2", durability=flow.durability)` (`RunControl` from `langgraph.runtime`, one fresh instance per attempt, kept by the runner so shutdown can drain it)
3. §5 input paragraph:
   - Before: `... on a recovery attempt \`None\` if the latest checkpoint already carries this \`run_id\`, otherwise the original input again (open check: checkpoint metadata propagation).`
   - After: `... on a recovery attempt \`None\` if the latest checkpoint's \`metadata["run_id"]\` (read with \`checkpointer.aget_tuple\`) equals this \`run_id\`, otherwise the original input again. \`run_id\` goes in \`config["metadata"]\` as a \`str\`. LangGraph applies the same rule itself (re-sending the original input with the same \`metadata.run_id\` is a re-entry), so the check is a safety belt, not the only guard (S1).`
4. §8 row "Graceful shutdown":
   - Before: `call \`RunControl.request_drain()\` on running runs (checkpoint at the next superstep, \`GraphDrained\`), put them back to \`pending\` and defer them`
   - After: `call \`RunControl.request_drain()\` on running runs: running nodes are not cancelled, their superstep finishes and checkpoints, then \`astream\` raises \`langgraph.errors.GraphDrained\` before the next superstep (a run in its last superstep just completes); put drained runs back to \`pending\` and defer them; the requeued attempt resumes with \`None\` (S1)`
5. §14 "Open checks": delete the rows `Checkpoint metadata carries \`metadata.run_id\` from the config`, `Runtime context reaches nodes when a graph declares no \`context_schema\``, and `\`RunControl\` import path ...`. Optionally add: `Checkpoint \`metadata.run_id\` round-trip on \`AsyncPostgresSaver\` (verified in source only, S1)`.

## Impact on dependent tasks

- T14 (flow registry): no need to require or inject `context_schema`; do not fail validation on its absence. If a flow declares a `context_schema` other than `RunContext`, the runner's instance is still passed unchanged (no coercion of non-dicts).
- T16 (runner):
  - Pass `control=RunControl()` per attempt and register it where shutdown can reach it; never reuse it across attempts.
  - Catch `GraphDrained` explicitly before generic error handling (it is a `GraphBubbleUp`, not a failure): status back to `pending`, no error row. A run that finishes after drain was requested is a normal success.
  - Put `run_id` (as `str`) and `thread_id` in `config["metadata"]`; recovery reads `aget_tuple(...).metadata.get("run_id")` to choose `None` vs original input. For runs whose input was `Command(resume=...)`, either choice continues correctly (measured).
  - Event mapping (T12/T16): v2 parts are dicts keyed `type/ns/data` (+ `interrupts` on `values`); interrupts arrive as `updates.__interrupt__` and in `values.interrupts`; `messages` metadata already carries `run_id`/`thread_id` and `langgraph_node`.
- T26 (graceful shutdown): drain waits for in-flight nodes, so `shutdown_grace_s` must exceed the longest node timeout (already in design); `request_drain` is thread-safe, so calling it from the signal path is fine; the drained thread is left with `next` set and resumes with `None`.

## Not verified

- Drain with parallel branches in one superstep and with `create_agent` subgraphs (expected to follow the same superstep rule; not measured).
