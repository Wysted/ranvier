# S5: ProcessPoolExecutor.kill_workers and langgraph on Python 3.14

Date: 2026-11-04. Brief: `docs/tasks/S5-process-pool-py314.md`.

## Question

1. On CPython 3.14.5+, what does `ProcessPoolExecutor.kill_workers()` do with a forkserver pool: effect on the running and pending tasks, and how to recycle the pool after a timeout?
2. On 3.13 (no `kill_workers`), what is the smallest correct way to kill a stuck worker and recycle the pool?
3. Do langgraph and langgraph-checkpoint-postgres import and run a small graph on 3.14?
4. What single `limits.py` API behaves the same on both versions?

## Results

### Check 1: `kill_workers()` on 3.14 with forkserver: PASS

Python 3.14.8, stdlib only. The default start method is already `forkserver` (`default_start_method=forkserver`).

Source (`314/process.py:978-1047`): `kill_workers()` is `_force_shutdown(_KILL)`. It sets `_force_shutting_down` under `_shutdown_lock` (gh-152967, so no replacement worker is spawned), copies `_processes`, calls `shutdown(wait=False, cancel_futures=True)`, then `Process.kill()` (SIGKILL) on each live worker. It does not join. Docs: "Added in version 3.14", and "After calling this method the caller should no longer submit tasks to the executor."

Observed (`pool_check.py`, 2 workers; A is stuck, B is running, C and D are queued):

```
[1] A timed out after 1.0s; asyncio future cancelled=True
[1] before recycle: workers=[35526, 35529] states=['R (running)', 'S (sleeping)'] B.running=True C.running=True D.running=False
[1] recycle via kill_workers: call took 0.14 ms
[1] B running: BrokenProcessPool(A process in the process pool was terminated abruptly ...)
[1] C pending: BrokenProcessPool(...)
[1] D pending: cancelled
[1] old workers after 0 ms: {35526: 'gone', 35529: 'gone'}
[1] new pool works: pids=[35587, 35590] reused_old=False
[1] submit to a killed pool: RuntimeError: cannot schedule new futures after shutdown
[2] 5 recycles: killed=6 still_present=[] manager_threads=1 (expect 1) ... mp.active_children()=1
[3] terminate_workers, SIGTERM-ignoring worker after 1 s: ['R (running)']
```

What this shows:
- **Cancelling the asyncio side does not stop the worker.** The future from `run_in_executor` reports `cancelled=True`, but the worker is still `R (running)`. Only a kill stops it, and the same holds when the caller is cancelled (for example a client disconnect).
- **The call is non-blocking** (0.14 ms) and the forkserver reaps the killed workers at once: no zombies and no orphans after 5 recycles. The old pool's manager thread exits (1 left, the live pool's), and the interpreter exits normally (`real 4.578s` is the sum of the script's sleeps).
- **Running tasks** (B) fail with `BrokenProcessPool`. **Queued tasks** split two ways:
  - Tasks already moved into the call queue (C) count as running. The call queue holds `max_workers + EXTRA_QUEUED_CALLS`, with `EXTRA_QUEUED_CALLS = 1` (`314/process.py:118,834`), and `set_running_or_notify_cancel()` runs when a task enters it (`314/process.py:486`). These fail with `BrokenProcessPool`.
  - Tasks still in the pending work items (D) are cancelled.
- **Recycle means replacing the pool**, because a killed executor rejects new work (`RuntimeError`). Pattern: create a new `ProcessPoolExecutor` and swap it in, then kill the old one.
- **Use `kill_workers()`, not `terminate_workers()`.** `terminate_workers()` (SIGTERM) does not stop a task that ignores SIGTERM: still `R (running)` after 1 s.

### Check 2: fallback on 3.13: PASS (uses one private attribute)

Python 3.13.16. `has_kill_workers=False`, and the default start method is `fork`. The forkserver context must therefore be passed explicitly so both versions behave the same.

The smallest correct fallback is a backport of 3.14 `_force_shutdown(_KILL)` (`bench/spikes/S5/pool_check.py`, `kill_pool`):

```python
kill = getattr(pool, "kill_workers", None)
if kill is not None:
    kill()
    return
procs = dict(pool._processes or {})  # private: pid -> multiprocessing.Process
pool.shutdown(wait=False, cancel_futures=True)
for proc in procs.values():
    try:
        proc.kill()
    except (ValueError, ProcessLookupError):
        continue
```

The 3.13 output matches 3.14 line for line: B and C `BrokenProcessPool`, D cancelled, workers gone in 0 ms, new pool OK, 6 kills with nothing left, 1 manager thread, normal exit (`real 3.033s`).

- **Private attribute used: `ProcessPoolExecutor._processes`.** It exists in both versions (`313/process.py:706,816`), and 3.14's own `kill_workers` reads it (`314/process.py:999-1000`).
- **Why the private attribute is unavoidable:** stdlib 3.13 offers no public way to find which processes belong to a pool.
  - `multiprocessing.active_children()` does list forkserver workers (`mp.active_children()=1` above), but it returns every child of the process, so it would also kill unrelated children.
  - Having each worker report its pid through an `initializer` takes more code and is open to pid reuse.
- **The gh-152967 race does not apply in our use, but only under one rule.** 3.13 lacks `_force_shutting_down`. On 3.13, workers are spawned only from `submit()` under `_shutdown_lock` (`313/process.py:818-840`). The wrapper swaps in the new pool before it kills the old one, and all submits come from the event-loop thread, so no submit can race with the kill. That rule must hold in T09.

### Check 4: one `limits.py` API for both versions: PASS (with a design change)

`recommended_check.py` runs both shapes on both interpreters, and the output is identical on 3.13.16 and 3.14.8:

```
[i] SharedPool: stuck=TimeoutError healthy=BrokenProcessPool (want TimeoutError, int) recycles=1
[i] SlotPool: stuck=TimeoutError healthy=int (want TimeoutError, int) recycles=1
[a] concurrent timeouts: ['TimeoutError', 'TimeoutError'] recycles=2 (expect 2)
[b] caller cancelled: recycles=3 (expect 3) live workers before cancel=['gone'] (expect all gone)
[c] SharedPool(bounded=False): queued task TimeoutError recycles=1 (expect 0) healthy=['BrokenProcessPool', 'BrokenProcessPool'] (expect int, int)
[c] SharedPool: queued task TimeoutError recycles=0 (expect 0) healthy=['int', 'int'] (expect int, int)
[c] SlotPool: queued task TimeoutError recycles=0 (expect 0) healthy=['int', 'int'] (expect int, int)
[e] crashing task: BrokenProcessPool recycles+=1 (expect 1) next call ok=True
[f] all idle workers killed, next 4 calls: ['int', 'BrokenProcessPool', 'int', 'int'] ...
[z] after close: mp.active_children()=0 (expect 0)
```

**Problems with the design's shape (one pool, kill it on timeout):**
- **It breaks §8 "a failing run never touches another".** `kill_workers` kills every worker in the pool, so a CPU tool that times out in run X fails the healthy CPU call of run Y with `BrokenProcessPool` (`[i] SharedPool`).
- **A queued task that times out can trigger a needless kill.** Without a bound on submissions, a task sitting in the call queue reports `running()`, so `cancel()` fails on its timeout and the wrapper kills healthy work. `[c] SharedPool(bounded=False)` shows exactly this: the queued task times out, `recycles=1`, and both healthy tasks fail with `BrokenProcessPool`. `SharedPool` avoids it by capping submissions with `asyncio.Semaphore(workers)`.
- **Two concurrent timeouts on one pool need a guard,** or the second kill would hit the replacement pool (`pool is not self._pool`).

**Recommended: `SlotPool`.** It has `cpu_workers` single-worker `ProcessPoolExecutor`s plus an `asyncio.Queue` of free slot indexes, and each call holds one slot exclusively:

```python
async def run(self, fn, *args, timeout_s):
    async with asyncio.timeout(timeout_s):  # also bounds the wait for a free slot
        slot = await self._free.get()
        try:
            pool = self._pools[slot]
            try:
                fut = pool.submit(fn, *args)  # raises at once if its idle worker died
                return await asyncio.wrap_future(fut)
            except BrokenProcessPool:  # worker crash or OOM kill
                self._recycle(slot)
                raise
            except asyncio.CancelledError:  # timeout or caller cancelled
                if not fut.cancel() and not fut.done():
                    self._recycle(slot)  # running: only a kill stops it
                raise
        finally:
            self._free.put_nowait(slot)


def _recycle(self, slot):
    old, self._pools[slot] = self._pools[slot], self._new()  # swap first, then kill
    kill_pool(old)  # kill_workers or the 3.13 backport
```

What it gives:
- **Isolation:** recycling a slot touches only its own worker (`[i] SlotPool`).
- **No guard needed:** only one task is ever submitted to an executor, so the call-queue pre-feed cannot hit a queued task (`[c] SlotPool`), and the slot owner is the only one who can recycle it (`[a]`).
- **Orphans cleaned up:** a cancelled caller (`[b]`) and a crashed worker (`[e]`) both leave no orphan, and later calls work.
- **One known blip:** a worker killed from outside while idle fails the next call on that slot once, then the slot heals (`[f]`).
- **Cost:** one manager thread per slot (2 by default) instead of one for the whole pool.
- `asyncio.wrap_future(pool.submit(...))` is what `loop.run_in_executor` does (`314/asyncio/base_events.py:898-899`). The explicit form keeps the concurrent future so the wrapper can try `cancel()`.

## Impact on design

Proposed `docs/design.md` edits. The orchestrator applies them.

1. §8 table, row "CPU-heavy tools" (line 368).
   - Before: ``| CPU-heavy tools | `isolation = "process"`: `ProcessPoolExecutor` (forkserver), timeout recycles the pool (`kill_workers`, 3.14) | `limits.cpu_workers` (2) |``

## Impact on dependent tasks

T09 (`limits.py`):
- **Implement the `SlotPool` shape above**, not one shared pool. The brief's `recycle()` becomes per-slot and private (`_recycle(slot)`). `run(fn, *args, timeout_s)` stays as the public API. `close()` kills every slot (`kill_pool` per executor); it goes in the `AsyncExitStack` after admission is drained.
- **Pass `mp_context=multiprocessing.get_context("forkserver")` explicitly.** 3.13 defaults to `fork`.
- **Recycle in three cases:** on timeout and on caller cancellation when `fut.cancel()` fails, and on `BrokenProcessPool`. Otherwise a worker that dies on its own leaves the slot broken for good.
- **Swap the new executor in before killing the old one,** and submit only from the event-loop thread (keeps the 3.13 backport race-free).
- **Mark the 3.13 branch** with `shortcut: private ProcessPoolExecutor._processes on 3.13, delete when requires-python >=3.14 (OD-7 b)`.
- **Unit test hints, all proven in `recommended_check.py`:** a stuck SIGTERM-ignoring busy loop times out and its pid disappears from `/proc`; a parallel healthy call still returns; a queued call that times out causes no recycle; a `SIGKILL`-self task fails once and the next call works.
- **Stats for T33:** free slots (`self._free.qsize()`), recycles count.
- **Error mapping (T27 side):** `TimeoutError` → `tool_timeout`, `BrokenProcessPool` → a tool error `ToolMessage` (worker crashed). Neither needs a retry in the pool.
