# S2: mcp SDK v2 Client, session reuse, reconnect, failure isolation

Versions (printed by the script): Python 3.14.8, `mcp==2.3.0`, `mcp-types==2.3.0`, `httpx2==2.16.0`,
`anyio==4.16.0`, `starlette==1.10.0`, `uvicorn==0.54.0`, `langchain-core==1.7.6`
(`langchain-anthropic==1.7.10`, `langchain-openai==1.7.4`, `langchain-ollama==1.1.0` from `uv.lock`).

Command (repo root, about 40 s, everything on 127.0.0.1 or in-process, no secrets):

```
uv run python bench/spikes/S2/s2.py                 # all groups
uv run python bench/spikes/S2/s2.py reuse reconnect # or a subset: reuse reconnect isolation hosting content
```

The server is an `mcp.server.mcpserver.MCPServer` (FastMCP was renamed in v2:
`mcp/server/fastmcp.py` only raises `ModuleNotFoundError`) wrapped by a small ASGI middleware that
counts HTTP requests, JSON-RPC methods, `mcp-session-id` values, client TCP ports and
`Authorization` headers, and injects failures (non-2xx status, truncated body) for one tool name.
Every check runs in both connect modes: `mode="auto"` (the default; against a 2.3.0 server it
negotiates the stateless 2026-07-28 protocol) and `mode="legacy"` (initialize handshake, 2025-11-25,
stateful `mcp-session-id`), because real servers can be either.

## Summary

| Check | Result |
|---|---|
| 1. One Client reuses its session (sequential + concurrent) | PASS (both modes) |
| 2. Reconnect after a server restart | PARTIAL: works, but not by itself and not with the Client in the composition root's task |

## 1. Session reuse

**Question.** Does one `mcp.Client` entered once reuse its session across many sequential and
concurrent calls?

**Method.** `check_reuse`: enter one Client, `list_tools()`, 50 sequential `echo` calls, then 50
concurrent `slow(0.2)` calls with `asyncio.gather`; the server middleware counts.

**Result: PASS (both modes).**

```
[PASS] reuse mode=auto
    negotiated=2026-07-28 concurrent_wall=0.26s tool_calls=100 handshakes=1 session_ids=0 tcp_conns=50 ...
    http={'POST': 102} rpc={'server/discover': 1, 'tools/list': 1, 'tools/call': 100}
[PASS] reuse mode=legacy
    negotiated=2025-11-25 concurrent_wall=0.28s tool_calls=100 handshakes=1 session_ids=1 tcp_conns=105 ...
    http={'POST': 103, 'GET': 1, 'DELETE': 1} rpc={'initialize': 1, 'notifications/initialized': 1, 'tools/list': 1, 'tools/call': 100}
```

- One handshake per Client for its whole life (`server/discover` in auto, `initialize` in legacy).
- auto/2026-07-28 has no session at all (`session_ids=0`): each call is an independent POST; the
  server routes any non-handshake `mcp-protocol-version` header to the stateless modern handler
  (`mcp/server/streamable_http_manager.py:194`). "Session reuse" there means one Client, one
  negotiated version, one httpx2 connection pool.
- legacy keeps exactly one `mcp-session-id`, a GET stream, and sends DELETE on exit
  (`terminate_on_close=True`).
- 50 concurrent calls took 0.26-0.28 s, so calls on one Client are not serialized.
- Side note, not investigated: in legacy mode every HTTP request used a new TCP connection
  (105 ports for 105 requests); auto reused connections for sequential calls (50 ports).

## 2. Reconnect after a server restart

**Question.** What error surfaces, does the Client recover by itself or need re-entry, and what is
the minimal recovery code?

**Method.** `check_host_cancel`, `check_reconnect`, `check_connect_error_wrapper`: uvicorn on a
fixed local port, stop it, call, start a new server on the same port, call again.

**Result: PARTIAL.**

Findings, in the order T29 needs them:

1. **A transport error cancels the task that entered the Client.** `streamable_http_client` runs
   each POST with `tg.start_soon(self._run_request_post, ...)` (`streamable_http.py:680`) and
   `_run_request_post` has `try/finally` but no `except` (`streamable_http.py:346-361`). A `httpx2.ConnectError`
   therefore escapes into the transport task group, which belongs to the task that ran
   `Client.__aenter__`, and cancels it:

   ```
   [PASS] host-task cancel mode=auto
       call from another task while down: raised MCPError(code=-32000, message='Connection closed')
       root task: died after 0.19s of a 10s sleep: ExceptionGroup[httpx2.ConnectError('All connection attempts failed')]
   ```

   With the Client entered in the composition root (as design §7 says today), one call to an
   unreachable MCP server would cancel the API lifespan or the worker main task. Upstream issue
   python-sdk #1393 ("errors surface from the task group") is still open.

2. **The same Client does not recover; a Client cannot be re-entered.** After the failure the
   Client is dead (`Connection closed` for the caller, the entering task gets the
   `ExceptionGroup`). `Client.__aenter__` refuses re-entry (`client.py:455`) and the transport is a
   single-use generator. Recovery = a new `Client` and a new `streamable_http_client(...)`; the
   `httpx2.AsyncClient` can be kept.

3. **Minimal recovery that works (`OwnedClient` in the script).** Enter each Client in its own owner
   task (`async with Client(...): await stop.wait()`), never in the caller's or the root's task. On
   the next call, if the owner task is done, start a new owner. For legacy servers also restart on
   `MCPError` with code `INVALID_REQUEST` (-32600): that is how a stale `mcp-session-id` surfaces
   (`"Session terminated"` from the transport's 404 mapping, `streamable_http.py:424`, or the
   server's own body, `"Session not found"` from a 2.3.0 server). Do not retry the failed call
   (tool calls are not assumed idempotent).

   ```
   [PASS] reconnect mode=auto
       in-flight during shutdown: raised MCPError(code=-32603, message='Server returned an error response')
       call while down: raised MCPError(code=-32000, message='Connection closed')
       owner alive after that call: False
       call while down #2: raised ExceptionGroup[httpx2.ConnectError('All connection attempts failed')]
       after restart: ok ... 'c0' | ok ... 'c1' | ok ... 'c2'
       quick restart, same owner: ok ... 'q0' | ok ... 'q1' | ok ... 'q2' restarts=1
   [PASS] reconnect mode=legacy
       in-flight during shutdown: raised MCPError(code=-32000, message='SSE stream ended without a response')
       after restart: ok ... 'c0' | ok ... 'c1' | ok ... 'c2'
       quick restart, same owner: raised MCPError(code=-32600, message='Session not found') | ok ... 'q1' | ok ... 'q2' restarts=2
   ```

   "Quick restart" means no call while the server was down. auto/2026-07-28 then needs nothing
   (stateless); legacy fails exactly one call with -32600, then reconnects.
   A start attempt while the server is still down raises `ExceptionGroup[httpx2.ConnectError]`
   from `Client.__aenter__` (the "call while down #2" line).

4. **Connect failures can be made request-scoped with a 25-line httpx2 transport.**
   `ConnectErrorAs502` wraps `httpx2.AsyncHTTPTransport` and turns a `httpx2.TransportError` raised
   before any response into a synthetic 502. The SDK maps non-2xx to a request-scoped `MCPError`
   (the #2604 fix), so nothing reaches the task group:

   ```
   [PASS] connect-error->502 wrapper mode=auto
       while down: raised MCPError(code=-32603, message='Server returned an error response')
       root alive while down: True
       same client after restart: ok ... 'c0' | ok ... 'c1'
       root: finished normally
   [PASS] connect-error->502 wrapper mode=legacy
       root alive while down: True
       same client after restart: raised MCPError(code=-32600, message='Session not found') | (same)
   ```

   It cannot cover errors after the response started (see 3b), so the owner task is still needed.

## 3. Failure isolation (python-sdk #2604)

**Question.** Does one failing request kill concurrent requests on the same Client in 2.3.0?

**Method.** `check_isolation`: 8 concurrent `slow(1.0)` siblings plus, concurrently, a tool that
raises, injected HTTP 400/404/500, a call with `read_timeout_seconds=0.3`, and a call cancelled by
`asyncio.wait_for(..., 0.3)`; then one more call. `check_transport_isolation`: the same 8
siblings plus one call whose response is a 200 with `content-length: 1000` and a 17-byte body.

**Result 3a: PASS (both modes).** #2604 is fixed in 2.3.0 (non-2xx is turned into a request-scoped
JSON-RPC error in `_handle_post_request`, `streamable_http.py:398-431`):

```
[PASS] isolation mode=auto        (legacy identical except http_404)
    siblings_ok=True
    tool_raises: ok is_error=True text='Error executing tool boom'
    http_400: raised MCPError(code=-32603, message='Server returned an error response')
    http_404: raised MCPError(code=-32601, message='Not Found')        # legacy: -32600 'Session terminated'
    http_500: raised MCPError(code=-32603, message='Server returned an error response')
    read_timeout: raised MCPError(code=-32001, message="Request 'tools/call' timed out")
    caller_cancel: raised builtins.TimeoutError('')
    after: ok is_error=False text='alive'
```

A tool exception is a result (`is_error=True`), not an exception. In legacy mode an HTTP 404 is
indistinguishable from a lost session (-32600), so the restart rule in 2.3 also restarts on a
genuine 404; that costs one handshake, not correctness.

**Result 3b: FAIL (both modes).** A transport-level error on one request fails every in-flight
request on that Client and kills the owner task; the next call reconnects:

```
[FAIL] transport-error isolation mode=auto        (legacy identical)
    failing: raised MCPError(code=-32000, message='Connection closed')
    siblings: {'raised MCPError': 8}
    owner alive after: False
    next call: ok is_error=False text='next' restarts=1
    deaths=["ExceptionGroup[httpx2.RemoteProtocolError('peer closed connection without sending complete message body (received 17 bytes, expected 1000)')]"]
```

Same root cause as finding 2.1 (no per-request `except` in `_run_request_post`). Blast radius: one
MCP server's in-flight calls, each becoming an error `ToolMessage`; other servers and runs are not
touched as long as each Client has its own owner task.

## 4. In-process server for tests; headers

**Question.** ASGI transport vs a local port, and how an `httpx2.AsyncClient` with headers is
passed to `mcp.Client`.

**Result: PASS.**

- Headers: `Client(streamable_http_client(url, http_client=hc))` with
  `hc = httpx2.AsyncClient(headers={...}, timeout=httpx2.Timeout(30.0, read=300.0))`. The server saw
  the header both over a port and over ASGI (`auth_seen=['Bearer port']`, `['Bearer asgi']`).
  There is no `headers=` keyword (Context7, python-sdk `docs/client/transports.md`), and the caller
  owns and closes `hc`. Keep an explicit timeout: the SDK docs note httpx2's 5 s default would
  cut long tool calls.
- ASGI, no port (`check_asgi`, all four combinations of mode x `json_response` pass, 10 concurrent
  calls in 0.21 s):

  ```python
  srv = MCPServer("t")
  app = srv.streamable_http_app()
  async with srv.session_manager.run():                    # ASGITransport sends no lifespan events
      hc = httpx2.AsyncClient(transport=httpx2.ASGITransport(app=app),
                              base_url="http://127.0.0.1:8000", headers=..., timeout=...)
      async with hc, Client(streamable_http_client("http://127.0.0.1:8000/mcp", http_client=hc)) as c:
          ...
  ```

  The base URL needs an explicit non-default port: `streamable_http_app(host="127.0.0.1")`
  auto-enables DNS-rebinding protection with `allowed_hosts=["127.0.0.1:*", ...]`
  (`mcp/server/lowlevel/server.py:752-757`), and `http://127.0.0.1` (Host without port) got
  `421 Invalid Host header` in the first run. The Starlette lifespan is just
  `session_manager.run()` (`lowlevel/server.py:851`).
- Local port: `uvicorn.Server(uvicorn.Config(app, host="127.0.0.1", port=port))` started with
  `asyncio.create_task(server.serve())`, waiting for `server.started`, stopped with
  `server.should_exit = True`. Needed for restart tests; ASGI is enough for list/call/isolation.
- `Client(MCPServer)` connects in-process with no HTTP at all (2026-07-28 direct dispatcher);
  fine for result-mapping tests, not for transport behavior.
- After a new Client is created, the first `call_tool` triggers an implicit `tools/list` to learn
  output schemas (`mcp/client/session.py:1127`), visible as `tools/list: 1` in the reconnect and
  ASGI counters.

## 5. Content blocks to a LangChain ToolMessage (optional)

**Method.** `check_content`: a tool returns text, an image, a text resource and a blob resource;
`to_lc_blocks` maps them (text -> `create_text_block`, image -> `create_image_block(base64, mime_type)`,
text resource -> text block, image blob -> image block, other blob -> `create_file_block`; every
resource also goes to the artifact); a `StructuredTool(args_schema=<inputSchema dict>,
response_format="content_and_artifact")` is invoked with a tool call; the resulting history is
passed through each installed provider's private formatter offline.

**Result: PASS for the LangChain side.**

```
    wire blocks=['text', 'image', 'resource', 'resource']
    structured_content={'n': 21, 'double': 42}
    ToolMessage.content types=['text', 'image', 'text', 'image'] content_blocks=['text', 'image', 'text', 'image']
    artifact keys=['resources', 'structured_content'] resources=2
    anthropic: role=user tool_result inner=['text', 'image', 'text', 'image']
    openai chat/completions: role=tool content=['text', 'image_url', 'text', 'image_url']
    ollama: role=tool images=2 content='\ncaption\nnote'
```

- `args_schema` accepts the `inputSchema` dict as is.
- Whether the OpenAI/Azure Chat Completions API accepts `image_url` parts inside a `role=tool`
  message was not verified (no paid calls). Open check below.
- Server-side gotcha: a bare `mcpserver.utilities.types.Image` inside a returned list raised
  `PydanticSerializationError` in 2.3.0; `Image(...).to_image_content()` works.

## Impact on design (proposed `docs/design.md` edits)

1. §7 row "MCP port".

   Before:
   > Own adapter: one `mcp.Client` per server with its own `httpx2.AsyncClient` (headers, timeouts), entered in the composition root; lists tools once (paginated); ... wraps each call with the server semaphore and timeout; reconnects on session loss

   After:
   > Own adapter: one `mcp.Client` per server over `streamable_http_client(url, http_client=...)` with its own `httpx2.AsyncClient` (headers, `Timeout(timeout_s, read=...)`, a transport that turns pre-response connect errors into a 502); each Client is entered and held by its own owner task (the composition root only registers the owner's stop in its `AsyncExitStack`; it never enters a Client itself, because a transport error cancels the entering task, S2); lists tools once (paginated); ... wraps each call with the server semaphore and timeout; reconnect = new `Client` + new transport on the next call when the owner task died or a handshake-era server answers `INVALID_REQUEST` (stale session), under a per-server lock; the failed call is not retried

2. §8 row "Error isolation".

   Before:
   > Tool and MCP errors become error `ToolMessage`s; a failing run never touches another; supersteps are transactional

   After:
   > Tool and MCP errors become error `ToolMessage`s; a failing run never touches another, except that a transport failure after an MCP response started fails every in-flight call on that MCP server (each an error `ToolMessage`; the next call reconnects; mcp 2.3.0, python-sdk #1393); supersteps are transactional

3. §14 "Open checks", MCP row: replace the open text with
   > Resolved by S2 (`docs/spikes/S2.md`): one Client reuses its session (one handshake); restart needs a new Client (owner task + reconnect on next call); #2604 fixed in 2.3.0 for non-2xx, but transport-level errors still fail all in-flight calls on that server; blocks reach `ToolMessage`

   and add a new row:
   > OpenAI/Azure Chat Completions accept image parts inside `role=tool` messages (LangChain emits `image_url` parts there) | MCP results, profiles using OpenAI/Azure

4. Decision log (`_shared/decisions.md`, owned by the orchestrator): optional one line,
   "MCP Client held by a per-server owner task, not entered in the composition root | mcp 2.3.0 transport errors cancel the entering task (S2)".

## Impact on dependent tasks

**T29** (`agents/mcp.py`):

- Acceptance "entered in the passed `AsyncExitStack`" must change to: `open_mcp_sources` starts one
  owner task per server and registers its shutdown (set stop, await the task, do not re-raise its
  death) on the stack. `OwnedClient` in `bench/spikes/S2/s2.py` is the reference shape (about 70
  lines with docstring); add the per-server `asyncio.Lock` around restart that the spike skips (marked `shortcut:`).
- Build the transport as `streamable_http_client(url, http_client=hc)`; `Client(url_str)` cannot
  carry headers. One `httpx2.AsyncClient` per server, kept across reconnects, closed by the stack.
- Use `mode="auto"` (default): it handles both 2026-07-28 and handshake-era servers.
- Reconnect rule: owner task done, or `MCPError.code == INVALID_REQUEST` on a non-modern
  `protocol_version`. No automatic retry of the failed call.
- Map `MCPError` (including -32000 `Connection closed`, -32001 timeout, -32603 non-2xx) and
  `TimeoutError` to error `ToolMessage`s. `is_error=True` results come back as results, not exceptions.
- Tests: ASGI transport (explicit-port base URL, `session_manager.run()`) for list/call/concurrent
  calls with one failing (tool raise, injected non-2xx); a uvicorn local port for the restart test
  (feasible, see check 2). A truncated-body injection reproduces 3b if T29 wants a regression test.
- Both per-call timeouts stayed request-scoped: `read_timeout_seconds` (`MCPError` -32001) and caller-side cancellation (`asyncio.wait_for`, `TimeoutError`).
